## 1. What Ember is

A desktop IDE (macOS Apple Silicon, Windows, Linux) built on VSCodium (VS Code's open-source base, Electron, about 940 MB on disk, 99 bundled extensions) with its own extensions layered on: an agent extension (chats, review, board, Bonfire, settings UI, about 200 commands), a "Tab" next-edit extension, a theme and a defaults extension. Free; optional $5 "support" key (5 activations) via Polar, which only hides a reminder.

Thesis: the agent is **Claude Code itself** (run through the local CLI/Agent SDK on the user's own Claude plan, no API key, credentials never handled), and the IDE is the control room around it. "You stay the engineer": agents type, you read, review and can edit everything. No Ember cloud, no account, no telemetry; history and index live locally. Other models (ChatGPT sign-in, OpenRouter and similar, local servers) run inside the same Claude Code harness so rules, hooks and approvals behave identically.

Core organising rule: **one task, one branch, one pull request.** Claude never commits on the base branch; parallel work gets a git worktree; git is the only record (squash-merge to bring work over, reset-merge to undo, no shadow copy).

## 3. iPhone app

A PWA that talks to a small hub on the user's own computer (Tailscale, LAN, ngrok, Cloudflare tunnel or custom URL). Pairing by 6-digit code (5-minute expiry, limited attempts); each device gets its own revocable token (only a hash stored). iPad gets the same address with a sidebar and shortcuts. Push notifications through Apple/Google.

Information architecture (as far as public): opens on **Now**, a ranked list of everything needing the user across all open Ember windows, in the same order as the desktop Dashboard. Each item is a card with **one primary button** for that branch's next step (Answer, Merge #41, Open PR, Remove worktree, Delete branch); multiple-choice questions from the agent appear as buttons. Then a **Working** tab, a **Chats** list grouped by branch, and a chat view with a condensed transcript and thumb-placed send. Actions: answer, approve a command, open/merge a PR, remove worktree, stop an agent, resume, start a chat. Kept off the phone on purpose: settings, sign-in, terminals, rule edits, window screenshots.

What makes it good:
- It is a **queue, not a dashboard**: ranked by what each item unblocks (a question holding three stacked branches beats a PR awaiting review).
- **One card, one button, one next step.** The desktop board, tab dot, title bar, dock badge and phone all read one shared list, so counts never disagree.
- **Prompts go where you are.** A merge confirms on the phone after re-showing the PR; worktree removal names what is inside first. Never a dialog on an unattended desktop.
- **Staleness check on every tap**: if the branch changed since the phone loaded it, the action does nothing and says so.
- A deliberately **small surface**: only unblock-and-steer actions, no config.

## 4. Git, review and push model

- **Isolation**: base branch is never committed to by an agent. A branch is created before the first commit. Parallel chats run in worktrees under the repo's `.claude/worktrees`. A chat belongs to a **worktree, not a branch**, so switching branches keeps the chat (their first design said branch and failed its own review; they also dropped six ways to move a chat between locations).
- **Where a chat works is chosen before it starts**: this tab, a new branch, a background worktree, or an existing branch or PR.
- **Six branch states** drive everything: Needs you, Working, Waiting, Ready, Merged, Idle, each with one next step.
- **Landing**: open a PR; or bring the work into your own checkout as an uncommitted squash merge; or check the branch out in the main worktree. Auto-merge on green is opt-in; otherwise the human merges. PR check state shows in tab chips (yellow while running, cancelled not red).
- **Review tab**: numbered diffs, Keep or Undo per hunk, file or all; an "Everything" view gives one net diff per chat; a commit marks an edit kept only if the commit contains it byte for byte. **Agent Review** runs a bug pass and a separate security pass, flags "asked for, not done", pins findings under lines, and "Fix with Claude" sends one back to the chat that wrote the code. Rewind restores files changed by commands too.
- **Forge** is the human git UI (stage by line, AI commit message, branch graph); Issues merges GitHub and Jira into one table linked to branch, chat and PR.
- **Conflicts**: "Resolve conflicts with Ember" command.
- **Cleanup rule written after losing a file**: a worktree is kept if it has uncommitted, untracked, possibly-yours ignored files, a detached HEAD, or anything unchecked; a branch is deleted only when git proves it landed (cherry for merges, merge-tree for squashes). "Remove worktree" and "Delete branch" are separate labelled actions; manual removal lists exactly what would be lost. Same checks run from board, chat, plan cleanup and phone.

## 5. Agent control model

- **Three command levels**: ask for every command; run safe ones (read-only, tests, builds, type-check, lint, git-read); run everything. File edits never prompt, because review comes after, per hunk.
- **Safe means proven safe**: each command is parsed; an unreadable command is never safe. **Checks fail closed** (error or timeout blocks and names the failing check).
- **Always-ask list** below the top level, even for subagents: deleting trees, force-push, deleting remote branches, hard reset, forced clean, admin, pipe-to-shell, SSH keys and cloud credentials. Those prompts explain why and omit "always allow".
- **Git guardrails**: agents push only their own branch and open their own PR; any push, merge or rebase touching a protected branch needs an explicit instruction in chat; hooks are never skipped; the repo's own PR targets and naming rules are respected.
- **Steering while running**: queue or steer, stop the turn, stop all (chord), Plan and Ask modes, rewind, fork.
- **Bonfire**: a plan becomes to-dos with declared changes and dependencies; each gets worktree, chat, branch and PR; a reviewer agent checks each; passing work merges in order (stacked or after the parent); has a usage forecast and scheduled runs.
- **Compare**: one prompt to 2 to 4 models, each on its own branch, side-by-side diffs, keep the winner.
- **Notices**: voice announces when a chat needs you; reply by voice; "ask before quitting" while chats run.
- **Usage**: live 5-hour and weekly limits, usage page by day, model, project, account; multiple Claude accounts per folder or chat.

## 6. What is clever and why

1. **One ranked "needs you" list feeding every surface** (dashboard, tab dot, dock, phone). Attention is the scarce resource; this makes it a single queue with one next action each.
2. **Git as the only source of truth.** No shadow state to drift; everything is inspectable and redoable in a terminal. Trust comes from boring primitives.
3. **Chat belongs to a worktree, branch is read live.** Matches how developers actually switch branches mid-task.
4. **Review after, not approve before, for edits** (cheap, reversible, hunk-level) **and approve before for irreversible commands** (fail closed). Friction spent only where damage is permanent.
5. **The cleanup scar**: strictest default for anything that deletes; label actions by outcome (Remove worktree vs Delete branch).
6. **Phone as unblock-and-steer only**, prompts routed to the device in hand, stale taps refused.
7. **Same config files as the CLI.** No lock-in, no second brain; the UI is a lens over files the user already owns.
8. **Review findings routed back to the author chat** ("Fix with Claude", chat that wrote this line): closes the loop between reviewing and fixing.
9. **Decide where work happens before it starts** (tab, new branch, background worktree, PR) rather than moving it later.

## 8. Design opportunities for Trantor (our terms, no code)

1. **A single "Needs you" queue.** Merge decisions, gate go/no-go, asks, stalled seats, review findings and PRs into one ranked list ordered by what each unblocks, with one primary button per item. Feed it to the desktop home, the dock badge, and the phone Decisions tab so counts always match.
2. **Make the main checkout a first-class git target.** Teach the Git panel a scope switch: project main checkout vs a seat's worktree. Same stage, commit, push surface; mutations on main are guarded and clearly marked.
3. **Branch-per-card as the unit of work.** Each card owns a branch and (later) a PR; the card shows branch state (working, waiting for review, ready, merged) and one next step. Agents never commit to the base branch; protected-branch actions need an explicit operator instruction.
4. **A real review loop.** Hunk-level keep or undo on a seat's changes, a net diff per card, and "send this finding back to the seat that wrote it". Anchor cross-reviewer findings under the lines they refer to, including an "asked for, not done" check against the card text.
5. **Provenance in the editor.** Click a line, see which seat, card and message wrote it, and jump to that conversation. Natural fit because Trantor already records the event log.
6. **Visible control policy.** A per-project screen listing what agents may do freely, must ask about, and may never do (force-push, deleting trees, touching credentials, protected branches), with fail-closed behaviour and the reasons shown. Keep the autonomy dial, but show the rules under it.
7. **Dependency-aware plans (Bonfire-like).** Let Genesis or the Overseer turn a plan into cards with declared dependencies, each with its own branch, ordered merge, and an up-front cost forecast using the existing usage data.
8. **Race mode.** Send one prompt to two to four seats or models on separate worktrees, compare diffs side by side, keep one. Cheap to explain, strongly demonstrates the crew idea.
9. **Work items with depth.** Sync GitHub and Jira issues into the board, link each to branch, seat and PR, and show them in one table view.
10. **A teardown rule that never takes unlanded work.** Adopt the "keep it if unsure" principle for seat and worktree cleanup, with outcome-named actions ("remove worktree", "delete branch") and a listing of what would be lost.
11. **Phone: confirm where you are.** Route merge, push and removal confirmations to the phone with the item re-shown, refuse taps on stale state, and keep config off the phone. Consider a Now-style home that is only a queue.
12. **Saved layouts and a zen/editor-first mode** so developers who want an IDE feel can collapse the crew chrome, and a "Trantor-aware" settings page that edits the same project files the CLIs already read rather than a second store.
13. **Keep the moat visible.** Ember has no cross-agent bus, lateral review or costs across seats; surface those as the reasons to choose Trantor, not features to imitate.

## Design lessons for Trantor's developer mode and the IDE-to-orchestrator trust ramp
(Our words; ideas not code or assets.)

1. **One honest "do I have to do anything" screen beats a feed.** Ember's Dashboard opens with a sentence ("Nothing needs you now"), then two boxes: urgent (blocked on you) and calm (your move whenever; "nothing is blocked"). Each metric says what it counts and what to do about it. Trantor's operator view should lead with the same split, and treat "time agents spent waiting on the human" as a headline health number, not an afterthought.
2. **Trust is a ladder with named rungs the user can see and move.** Ember has four gears: Ask (read-only) → Plan (propose, you approve) → Agent with approvals → Run everything, plus a permission level per chat (ask / safe commands / everything), and the defaults are explicit about the risk. Edits are never gated beforehand; they are reversible afterward (Keep/Undo). Commands ARE gated beforehand because they are not reversible. For Trantor: gate by reversibility, not by tool type, and show the rung the seat is on in every seat row.
3. **Make the approval card tiny, loud, and answerable in one key.** Gold edge, one-line why, three buttons with keys (Run/Skip/Always run), always pinned above the composer, never pushed out of view, typed text never counts as consent. "Always run" saves a visible, scoped, removable rule, so the ramp climbs by the user's own clicks and every rule is listed in Settings. Trantor should record approval decisions the same way: each "yes" is a candidate standing rule with a scope label, shown in one list.
4. **Branch = chat = worktree = PR is the unit of agent work.** Their branch picker names which chat owns a branch and offers "Open tab"; the chat list can group "one card per worktree with its branch, PR and tab"; Dashboard turns finished branches into "8 files not committed / Open a PR" chores. Trantor seats already map to branches (seat/glm, seat/qwen): surface the branch→seat→card→PR chain as one object and make "finish this branch" a one-button next step.
5. **Review is per-hunk, in place, with an undo that is always available.** Pending changes are marked in the gutter, with Keep/Undo per change, per file, per chat, and an Undo-of-Keep. Every git object (commit, hunk, file) has "Add to chat", "Explain", "Check for bugs". For Trantor: card-level "accept/reject" should drill down to hunks inside the same UI and every agent verb should hang off whatever the human is looking at.
6. **Separate the reader from the writer.** Agent Review is explicitly read-only, with Quick/Deep, a scope, and findings that become Problems the user chooses to send to a fixer. A first rung on the trust ramp that costs the user nothing: let the orchestrator audit a branch before it is allowed to change anything.
7. **Provenance you can click.** Agent Blame (hover a line → chat → exact message), commits co-authored by the model, usage per subagent, "Last turn: which rules fired". Trantor's ledger/verify gate should be reachable from a line of code the same way.
8. **Parallel attempts as a first-class gesture.** "Try several" (N models, N worktrees, compare, keep one, safe cleanup with a checklist) and Bonfire (plan to-dos as a dependency board, one PR per to-do, you merge). This is the same shape as the Trantor crew; the lesson is the board UI: columns by dependency, cards that say where each to-do is and what button is next, and you remain the merge gate.
9. **Settings that explain their provenance.** Every row shows default/changed, scope (me / this project / team), and where it is saved. The Repository page even renders the "working agreements" every agent gets (one task one branch, protected branches need your words, final gate = CI green not local green) as toggles. Trantor's developer mode should ship the same: a human-readable contract page that the seats are held to, editable per project.
10. **Remote is a PWA served by the Mac with three honest transports** (Tailscale recommended, same Wi-Fi, public link), each listed with its exact trade-offs, off by default, pair per device. Phone can lower a chat's permission level but cannot raise it to Run everything. A good rule for Trantor's phone view: the phone may tighten, never loosen.
11. **Quiet by default, loud when it matters.** Notifications only when the app is backgrounded, optional spoken alerts that name the item, status-line timers on waiting items. Counters "N needs you / N working" in the chat list header are the whole attention model.
12. **IDE-to-orchestrator ramp for Trantor:** (a) Observe: Dashboard + read-only review. (b) Ask/Plan: proposals only. (c) Agent with approvals, edits reversible. (d) Standing rules grown from approvals. (e) Parallel seats on isolated worktrees with a human merge gate. (f) Unattended runs only after the rules list shows the user's own earned yeses. Ember does (a)-(e) in one app and deliberately leaves merge and the protected branch to the human.

## 4. Pull requests and Watch PR
No PR or "watch" UI was reachable without signing in (our branch is main). Read from Ember Help instead (54-help-forge-*, 55-watchpr-p0 to p4):
- The PR line is described above. Merge asks first and is blocked for drafts, conflicts, failed/running checks, or missing review; fork PRs are not treated as the branch's.
- "Watch a pull request": a chat watches one open GitHub PR about once a minute and fixes failing checks, resolves merge conflicts and addresses new review comments until green. It never merges, closes, approves, labels or edits the PR. Start with `/babysit` or `/babysit 123` in chat, the Command Palette "Watch PR...", the chat's "Watch PR" offer after a push, or "Fix with Claude" on the PR line. Needs the `gh` CLI signed in and an `origin` remote. Status line shows "Watching #123 · CI running / Fixing 2 failed checks / Resolving conflicts / Addressing 1 comment / Green / Stuck", with Pause, Continue, Stop. Stuck = same problem survives 3 attempts or 10 turns with no green. Waits while checks or the chat run so fixes do not stack. Settings: `ember.babysit.updateStrategy` merge (default) or rebase (force-push only with `--force-with-lease`, enforced on the commands, plain `--force` never), `ember.babysit.replyToComments` off by default. CI logs and comments go to the chat as data, not instructions.

## 5. Agent Review and findings (57-ar-p0 to p7, 59-rc-p0 to p3 help pages)
- Review your branch: Scope, Check for bugs; Quick vs Deep (`ember.review.deepDefault`); Security review as a separate pass (`/review-security`, `/review` slash commands hand uncommitted changes to read-only subagents). Review a chat's changes checks "against what you asked" (Major finding "Asked for, not done" has no line) plus bugs, and lists "Couldn't check" items. Review every commit via `ember.review.onCommit`. Includes untracked files, honours .emberignore and CLAUDE.md/rules.
- What a finding looks like: a card with a pill (MAJOR gold, MINOR blue, FIXED green dimmed), `file:line`, a bold title ("Open redirect through a backslash path"), one explanatory sentence, and buttons "Fix with Claude" (sends to a chat, marked "Sent to the chat") and "Dismiss". "Fix all" at the top. Click file:line to open it in the diff. Same findings appear in the Problems panel and as editor squiggles.
- Under a line: on the review page a finding about a line is drawn as a card directly under that line in the diff (59-rc-p0.png), with the same Fix with Claude / Dismiss buttons.
- Dismissal is remembered per repository by file + wording + the lines around; reappears if code changes; Critical is never silenced.
- Empty state: "Nothing to review: no changes against main" with "Pick another base" / "Review the last commit"; "No issues found" means something was read.
- Review page for a chat: changed files left (+/- counts), diff centre with line numbers (added green, removed clay, "15 unchanged lines" fold), Agent Review right; Keep file / Undo file, Keep all / Undo all; "Pending" vs "Everything" switch; "Open side by side".

## 6. Merge conflicts (61-conf-p0 to p2 and 54-help-forge-p17/p18)
Not reachable (no merge in progress). Per help: a banner shows what is paused (merge, rebase, cherry-pick, revert) and how many files conflict. Per file: Take ours, Take theirs, or Merge editor; then Mark resolved (or stage); then Continue (git makes the commit or continues the rebase). Or Abort (asks first, restores pre-start state), or "Resolve with Claude" (opens a chat that edits the conflicted files; its edits wait for your review). The sidebar shows the same Continue/Abort. In Source Control, "Resolve Conflicts with Ember" starts an Agent chat with all conflicted files attached; Claude keeps both sides' intent, removes markers, runs quick checks, and never stages or commits. When git fails, a card shows a short title, one sentence, a fix button, "Show git's output", "Ask Claude", and x to dismiss.

Other behaviours worth noting: Discard copies to the Trash first so work is recoverable; Undo last commit restages and restores the message; "Generate Commit Message" uses Haiku by default and never names Claude (`ember.git.keepClaudeOut`); `ember.forge.enabled` can turn Forge off and fall back to plain VS Code SCM.

## What Trantor's own source-control screen should take from this (our words)
1. One screen, three zones: a sidebar summary (branch, sync state, last fetch, anything mid-flight), a full tab with Changes and History, and the diff always beside the list. Keep the sidebar tiny and push depth to the tab.
2. Name the target on the commit button ("Commit to main") and keep amend, push, sync as variants of one split-button. Disable it with the reason ("Stage something first").
3. Make staging granular and obvious: file, hunk, and line, with the hover buttons labelled by tooltip. Show staged and unstaged as separate groups with Stage all / Unstage all / Discard all, and always confirm destructive actions by naming what is lost. Copy discarded work to a recoverable place.
4. History: one search box with `author:`, `file:`, `message:`, a Current branch / All branches switch, and an optional lane graph that hides during search. Commit detail with stats, parent, and a short fixed toolbar (open remote, add to chat, review, branch from here, more).
5. A branch picker that shows where each branch lives (main checkout, its own worktree, another tab) and which agent is on it, with an Open action per row. This maps directly onto Trantor seats and worktrees: show seat name and state per branch.
6. Treat agent work as first-class in git: "unreviewed edits from agents" card with a review action, a warning when an agent is running on the branch, and a prompt before switching branches under a working agent (wait, or stop and switch).
7. Review findings as cards under the line they concern (severity pill, file:line, one-sentence reason, fix and dismiss), with dismissal remembered per repo and re-raised when the code changes. Offer Bugs vs Security and Quick vs Deep, and label costly modes.
8. Pull request line with checks, review state and merge method, merge disabled with its reason. A "watch this PR" loop that fixes checks, conflicts and comments but never merges, with Pause/Continue/Stop and a "stuck after N tries" rule. This is the closest fit to a Trantor seat task.
9. Conflicts: a banner with per-file Take ours / Take theirs / Merge editor / Mark resolved, plus Continue and Abort, and an optional hand-off to an agent that never stages or commits.
10. Errors as a card: short title, one plain sentence, one fix button, show output, ask an agent, dismiss.
Avoid: no split/unified toggle was visible in the diff (side-by-side only via the editor), and the Forge History toolbar swaps Check for bugs and "through HEAD" in place, which hid the seventh icon until hover. Make both discoverable.
